## 3. Browser path (traced, with gaps)

```
index.html
  └─ src/main.ts
       ├─ register service worker (/dev-sw.js?dev-sw in dev, /sw.js in prod)
       │    generated by vite-plugin-pwa `injectManifest` from worker/sw.ts
       └─ turbo-frame#inbox src = /local/inbox   (only after a controller exists)

worker/sw.ts                                   service worker
  └─ Hono app, basePath /local
       ├─ GET  /counter        → worker/services/counter.ts
       ├─ POST /counter/increment
       └─ GET  /inbox          → InboxTransportSelector
                                   ├─ native: postMessage to page bridge
                                   └─ web:    fetch(/api/v1/inbox)
                                                └─ dev proxy → Python API
                                                     → UniFFI → Rust → IMAP

worker/database.ts                             dedicated worker (MessagePort RPC)
  ├─ navigator.locks exclusive "database owner" (5 s timeout)
  ├─ per-Worker import of vitest-ignored sqlite3.mjs + sqlite3.wasm (3.54.1)
  ├─ installOpfsSAHPoolVfs({ name, preserveOnInitFailure: true })
  ├─ new OpfsSAHPoolDb("/mail.sqlite3") + PRAGMA synchronous=FULL, foreign_keys=ON
  ├─ drizzle(sqlite-proxy) adapter, rowMode "array"
  └─ answers `counter-service` messages

src/database.ts                                spawns the DB worker,
                                               forwards `counter-service`
                                               ports from SW → DB worker
```

Confirmed gaps, each verified by reading the code:

1. **The SQLite/OPFS/Drizzle path is unreachable from the UI.**
   `src/database.ts` is never imported by `src/main.ts` or anything else.
   `worker/sw.ts` registers `/counter` and `/counter/increment`, but no page
   calls them. The only durable table today is `prototype_state` (a counter).
2. **There is no task UI.** `index.html` contains a `turbo-frame` and a loading
   message; there is no form, no list, no Stimulus controller of our own.
   `data-controller="bridge--inbox"` is served by the Hotwire Native bridge
   package, not by project code.
3. The only browser E2E spec (`app/tests/inbox.spec.ts`) covers the mail inbox
   against GreenMail via testcontainers. Nothing covers local persistence.
4. `drizzle-orm/sqlite-proxy` is wired so that `run` discards rows and only
   `get`/`all` return data; any new service must respect that.

Reusable as-is or near-as-is: the SW registration + controller-change handshake,
the Hono-in-service-worker skeleton with `basePath("/local")`, the
`fetch`-event origin/path guard, the workbox `injectManifest` configuration,
the SQLite WASM 3.54.1 vendored runtime, the SAH-pool + Drizzle adapter, the
dedicated DB worker, and the Web Locks single-owner pattern.

## 4. iOS path (traced, with gaps)

```
AppDelegate.swift
  ├─ Hotwire.registerBridgeComponents([InboxComponent.self])
  ├─ Hotwire.config.makeCustomWebView: limitsNavigationsToAppBoundDomains = true
  └─ webView.isInspectable = true

SceneDelegate.swift
  └─ Navigator(startLocation: https://<developer-private-host>)

Info.plist
  └─ WKAppBoundDomains = [ <same developer-private-host> ]

InboxComponent.swift  (BridgeComponent name "inbox", event "listInbox")
  ├─ validates correlationId is a UUID and 1 ≤ limit ≤ 50
  └─ InboxService.list(limit:)

InboxService.swift
  ├─ reads MALLEABLE_MAIL_{HOST,USERNAME,PASSWORD,...} from ProcessInfo environment
  ├─ single-flight gate (one request at a time)
  └─ Task.detached → Rust `listInbox(...)`  ← generated UniFFI Swift bindings
         (Generated/MailCore, produced by scripts/build-ios-simulator.sh)

Web side: src/inbox-bridge.ts (Stimulus BridgeComponent "bridge--inbox")
  ├─ connects, advertises service-worker/native capability over a MessagePort
  └─ zod-validates request and response on both ends
```

Confirmed gaps, each verified by reading the code:

1. **The iOS shell loads remote web content.** This matches the selected content
   model, but its private HTTPS host and app-bound domain must be replaced by
   safe project configuration. Bundled content is explicitly out of scope.
2. **PWA-style offline reopening and web SQLite remain unproven in WKWebView.**
   Test the selected origin, secure context, service-worker control and caching,
   worker routing, Web Locks and OPFS in slice 2. Reference code alone does not
   prove durable storage or cached startup.
3. **No native SQLite or Rust persistence exists, and none is required.** Task
   persistence belongs to TypeScript services in the web runtime on both platforms.
4. Swift bindings are generated into `ios/MalleableMail/MalleableMail/Generated/MailCore`
   and are build output, not template sources.
5. The Xcode scheme is named `MalleableMailSlice2`; project naming carries
   source history that must not be parameterized by copy.
6. Native checks are macOS/Xcode-only: `XCTest` unit tests inject a fake
   `Operation` into `InboxService`, and `app/tests/run-swift-greenmail.mjs`
   drives a simulator E2E through testcontainers + GreenMail.

Reusable as-is: the bridge-component shape (stable component name, explicit
event, correlation IDs, zod validation on the web side, `Encodable` responses on
the Swift side), the single-flight operation gate, the error-with-stable-code
pattern (`code`/`message`/`retryable`), and the split of `make.sh` targets for
`build_ios`/`test_ios`.

## 5. Rust scope

- `rustsrc` workspace: edition 2024, `license = "MIT"` declared in
  `[workspace.package]`, members `["crates/mail-core"]`.
- `mail-core`: `crate-type = ["cdylib", "rlib", "staticlib"]`,
  `uniffi = { version = "0.32.2", features = ["cli"] }`, `uniffi::setup_scaffolding!()`.
- Dependencies are all mail-specific: `imap`, `mailparse`, `html2text`,
  `native-tls`, `chrono`, `thiserror`.
- Public surface: `list_inbox`, `AccountConfiguration`, `ListInboxRequest`,
  `InboxMessage`, `MailError`, `MailErrorCode`.
- Bindings are generated for Python (test bridge) and Swift (iOS).

Implications for A6/A7: the *shape* (one crate, UniFFI records/enums, generated
bindings only at build time) is reusable. The mail contents and credentials are
excluded. Rust stays native-only permanently, for browser-inaccessible
capabilities such as TCP. The initial dedicated slice returns "hello from rust"
through web UI → Swift → generated UniFFI → Rust → web UI. Do not route task
CRUD through Rust, add native SQLite or compile this Rust core to browser WASM.

## 7. Licensing

- The source repository and `app-src/` contain **no LICENSE file**. The only
  licence statement is `license = "MIT"` in `rustsrc/Cargo.toml`. The owner has
  selected MIT for the template; retain applicable attribution and third-party
  notices and review copied files before publication.
- JavaScript dependencies worth carrying are permissive: Hono, Zod, Hotwire
  (Turbo/Stimulus/native-bridge), Vite, vite-plugin-pwa, workbox and Playwright
  are MIT; `drizzle-orm` is Apache-2.0. A generated project must keep its
  dependency notices intact.
- `app/worker/sqlite/3.54.1/` vendors the SQLite WASM build with an upstream
  README. SQLite is public domain; the bundled runtime and its provenance note
  must travel with the template unchanged.
- Excluded dependencies (imap, mailparse, html2text, native-tls) carry no
  obligation on the template.

## 8. Compatibility risks to prove later

- OPFS + SAH pool needs a secure context and Web Locks. The approved policy is
  one owning tab; other tabs show "App already open in another tab". Verify
  contention and ownership release with real tabs (slice 6).
- Service-worker caching, offline relaunch and OPFS inside WKWebView using the
  selected remote/Vite origin and app-bound domains remain unproven (slice 2).
  If this fails, stop for an owner decision, not a native-database fallback.
- `vite-plugin-pwa` `injectManifest` + `skipWaiting`/`clients.claim` gives
  immediate activation; mixed old/new app versions must be reasoned about in
  slice 7.
- The `sqlite-proxy` adapter drops rows on `run`; services must not depend on
  `RUN … RETURNING` through it.
- Nix owns the runtime; `make.sh` re-enters `nix develop` on every call. Root
  `mise.toml` only delegates. Any template must keep that contract (ADR 0005)
  without inheriting Django deployment assumptions.
